LinkedIn sidebar for Outlook on the web: the honest status

SenderFinder was built for Gmail first. Outlook on the web (outlook.live.com and outlook.office.com) is supported on a best-effort basis — it can work, it can break when Microsoft changes the page, and it is not the same promise as Gmail.

Last checked: 25 October 2026.

Add to Chrome Add to Microsoft Edge View the source on GitHub

The short version

If your team lives in Gmail, SenderFinder is designed for your workflow. If your team lives in Outlook on the web, you can install it and use it, but you should expect occasional rough edges and report them. If your team lives in Outlook for desktop, Apple Mail or another desktop client, SenderFinder cannot help: those apps do not expose the page a browser extension can read.

This page exists because “supported” is an unhelpfully binary word. Outlook web is a different application from Gmail, with a different page structure, different update cadence and two hostnames. Pretending the experience is identical would be dishonest. The extension does the same lookup; the part that attaches it to the mail page is what varies.

What works in Outlook on the web

The core of the product does not depend on the mail client. Keys, the provider waterfall, the name check, the cache, the history and the privacy model are the same in Outlook as in Gmail. What changes is how the extension finds the sender on the page.

In a normal Outlook web session, the extension can:

  • Show the sender's LinkedIn profile in the browser side panel when you open a message: photo, name, headline, company, location, local time and the profile link.
  • List the other people in the thread (other senders, To, Cc) and look one up when you click them, rather than looking everyone up automatically.
  • Run the free local signature scan for a linkedin.com/in link in the message body.
  • Use the same provider keys and the same per-lookup and daily caps as in Gmail.
  • Cache results and keep the history in your browser, so a repeat sender is never paid for twice.
  • Open the profile and pre-fill your Connect note. You still press Connect and Send yourself.

What does not work

The list is shorter and more important than the list above:

  • Outlook for desktop. SenderFinder is a browser extension for a web page. It does not run inside the desktop client.
  • Apple Mail and other desktop mail apps. Same reason: no page for the extension to read.
  • Firefox. Not supported yet. Chrome and Chromium-based browsers, including Microsoft Edge, are the target.
  • Every Outlook tenant. Custom domains, security add-ins and A/B layouts can change the page enough that the sender mark does not appear. The lookup is not wrong in that case; it simply has nowhere to attach.
  • A guarantee across Microsoft updates. Outlook web changes its DOM regularly. When it does, the extension may need an update, and the fix is reactive rather than instant.

Why “best-effort” is the honest label

Gmail offers a comparatively stable set of hooks around the message header and the thread. Outlook web has two public hostnames, more layout variation between personal and work accounts, and a habit of shipping changes without a compatibility window. A content script that finds the sender by a CSS selector is always one redesign away from doing nothing.

The project could hide that behind a confident “works everywhere” badge. It would be a worse product. Instead, the README and this page say best-effort, the extension is open source so you can see the Outlook content script, and issues are handled as they are reported. If the sender mark does not appear, that is a bug worth reporting, not a reason to pretend the client is unsupported.

It is also why Gmail remains the primary target. The most reliable experience is the one the project tests most, and the Outlook path is maintained rather than guaranteed. If Outlook is mandatory for your team, try it before you standardise on it.

How to try it and what to report

  1. Install SenderFinder from the Chrome Web Store or Microsoft Edge Add-ons. The install guide also covers the optional source route.
  2. Create one provider key (Monid or treg) and paste it into the settings page that opens on first install. Press “Test keys (free)” before the first lookup.
  3. Open outlook.live.com or outlook.office.com in Chrome or Edge, open a message and click the SenderFinder toolbar icon once. The panel stays open in that tab.
  4. If the magnifier mark does not appear next to the sender, open an issue on GitHub with the Outlook hostname, your browser version and the DOM of the sender block — not the email content.
  5. If the mark appears but the lookup fails, include the step that failed (for example hunter or apollo) and the status shown in the panel. Do not paste keys or addresses.

A screenshot of the sender area with the message text covered is usually enough. If the layout changes, the DOM of the sender block is what a fix needs.

Privacy is identical in both clients

Outlook does not change the data model. The address, display name and company domain go to the provider whose key you configured; the mail body is scanned locally and never sent; keys, cache and history stay in your browser. There is no SenderFinder server in the lookup path.

The anonymous daily counters are the same as in Gmail: counts, outcomes, provider-step totals, mail-client totals, rounded spend, version, language and a random installation ID. They are on by default, one switch turns them off and deletes the ID and anything unsent, and they contain no address, name, domain, profile field, key or message text. The privacy statement is the full list.

If Outlook is your main client

Use the web version in Chrome or Edge and treat the extension as an assistant, not infrastructure. Keep the sender lookup as a convenience and keep a manual fallback: search the thread for a LinkedIn link, search the web for the exact address, or search LinkedIn by name and company. The email-to-profile guide walks through those methods.

If you need a guaranteed sender sidebar in Outlook desktop, SenderFinder is the wrong tool today. A native Outlook add-in is a different product surface and is not on the roadmap. Saying so is more useful than a maybe.

If your team can choose, Gmail is the smoother path — not because the lookup is different, but because the page the extension attaches to is the one the project exercises most.

Questions about Outlook

What to expect before you install.

Does SenderFinder work in Outlook?

It works in Outlook on the web (outlook.live.com and outlook.office.com) on a best-effort basis. It does not work in Outlook for desktop, Apple Mail or Firefox.

Why is Outlook only best-effort?

The extension attaches to the mail page. Outlook web changes its page structure more often than Gmail and has more layout variation between accounts, so the sender mark can disappear after a Microsoft update. The lookup itself is the same; the attachment point is the fragile part.

What should I include in a bug report?

The Outlook hostname, browser and version, a screenshot of the sender area with the message text covered, and the DOM of the sender block. Do not include keys, email addresses or message content.

Is my data handled differently in Outlook?

No. The same rules apply in both clients: the address, display name and company domain go to the provider whose key you configured, the mail body is scanned locally and never sent, and there is no SenderFinder server in the lookup path.

Try it in the browser you already use

Outlook on the web works on a best-effort basis; Gmail is the primary target. Either way, one provider key and the default caps are enough to start.
